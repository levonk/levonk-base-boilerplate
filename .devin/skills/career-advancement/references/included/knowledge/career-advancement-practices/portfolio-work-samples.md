# Portfolio and Work Samples

## The "Portfolio as Proof" Principle

> **Showing is stronger than telling.** A resume claims you can do something;
> a portfolio proves it.

For roles where the work itself is the evidence — engineering, design,
writing, product — a portfolio converts a claim into a demonstration. A
recruiter who reads "built scalable web architecture" may believe it; a
recruiter who clicks through a well-documented repo with a clean README and
real commit history **knows** it.

## Portfolio Types by Role

| Role type | Portfolio format | Key elements |
|-----------|------------------|--------------|
| **Software engineering** | GitHub profile | 3–6 pinned repos, strong READMEs, visible contribution graph |
| **UX / design** | Design portfolio (site or PDF) | 3–5 case studies with process, not just final visuals |
| **Content / writing** | Writing samples (links or PDF) | 3–5 pieces spanning the target role's formats |
| **Product management** | Case studies + writing samples | Problem framing, approach, outcomes; PRDs if shareable |
| **Data / analytics** | Project repo or notebook | Reproducible analysis, clear narrative, visualizations |

## GitHub Repos (Technical Roles)

### Pin 3–6 best repos

Your GitHub profile's pinned repos are your **curated showcase**. Do not pin
everything; pin the repos that best demonstrate the skills the target role
needs.

| What to pin | What not to pin |
|-------------|-----------------|
| Repos with strong READMEs and clear purpose | Abandoned forks |
| Projects with real usage (stars, issues, PRs) | Tutorial / course exercises |
| Code that matches the target role's stack | Personal dotfiles (unless notable) |
| Projects you can speak about in depth | Repos with no commits in 2+ years |

### README quality matters

A pinned repo with a **one-line README** hurts more than it helps. A strong
README includes:

- **What** the project does (1–2 sentences).
- **Why** you built it (motivation / problem).
- **How** it works (architecture, key decisions).
- **How to run it** (setup instructions).
- **Tech stack** and your role if it was collaborative.

### Contribution graphs

A consistent contribution graph signals **active practice**. A long gap with
a sudden burst before a job hunt looks performative. Sustained, organic
contribution history is the strongest signal — but don't game it with
trivial commits; reviewers notice.

## Case Studies (Problem → Approach → Results)

Case studies are the **universal portfolio format** — they work for
engineering, design, PM, and data roles. The structure:

1. **Problem** — What was the situation? What needed solving?
2. **Approach** — What did you do? What decisions did you make and why?
3. **Results** — What was the outcome? Quantify if possible.

Each case study should be **1–2 pages** — long enough to show depth, short
enough to be read. For design roles, include visuals (before/after, flow
diagrams). For engineering, include architecture diagrams and key code
excerpts.

> A case study is not a project description. It is a **narrative of
> decision-making under constraints**. That is what hiring managers want to
> evaluate.

## When a Portfolio Outweighs the Resume

| Situation | Why the portfolio dominates |
|-----------|-----------------------------|
| **Creative roles** (design, writing) | The work is the qualification; the resume is secondary |
| **Early-career candidates** | Limited work history; projects prove capability |
| **Career changers** | Portfolio in the new field compensates for thin formal experience |
| **Open-source / community roles** | Public contributions are more credible than job titles |

In these situations, invest **disproportionate effort in the portfolio** and
treat the resume as a pointer to it.

## Referencing a Portfolio on a Resume

The portfolio link belongs in the **header**, next to your contact
information. Make it unmissable.

```
Jane Doe
jane@email.com | linkedin.com/in/janedoe | Portfolio: janedoe.dev
```

Or for GitHub-forward roles:

```
Jane Doe
jane@email.com | github.com/janedoe | linkedin.com/in/janedoe
```

Rules:

- **Use a clean URL.** A custom domain or GitHub profile link is ideal;
  avoid long query-string URLs.
- **Make the link clickable** in the PDF (and in any digital submission).
- **One link, not five.** Pick the primary portfolio destination; don't
  clutter the header with every profile.
- **Ensure the link works.** A dead portfolio link is worse than no link.

For aligning your portfolio with your LinkedIn presence, see
[linkedin-profile-optimization.md](linkedin-profile-optimization.md).

## The Maintenance Problem

A stale portfolio is a **liability**. Old work that no longer represents your
current skill level will be judged as your current skill level.

| Maintenance task | Frequency |
|------------------|-----------|
| Remove outdated projects | Quarterly |
| Update pinned repos when skills evolve | When you build something better |
| Check that all links resolve | Before every application |
| Refresh case study metrics if they've improved | Annually |

> Your portfolio is a living document, not a trophy case. If you wouldn't
> want a reviewer to judge you by a piece today, remove it.

## Keyword Alignment

Ensure your portfolio content uses the **same keywords** as the roles you are
targeting. A repo titled "cool-side-project" is a missed keyword opportunity;
one titled "real-time-event-aggregator" signals the stack and domain
immediately. See [keyword-engineering.md](keyword-engineering.md) for the
broader keyword strategy.
