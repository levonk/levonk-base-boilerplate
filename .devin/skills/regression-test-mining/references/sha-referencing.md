# SHA Referencing

Every regression test generated by this skill must reference the fix commit
SHA that exposed the original bug. This makes the lineage traceable: a future
reader can `git show <sha>` to understand the bug the test guards against.

## The Convention

The reference goes in a comment or docstring **on the test itself** (not the
file, not the `describe`/`module` block — the individual test). The format:

```
Regression test for fix <sha> — <one-line bug description>
```

The `<sha>` is the **full 40-character SHA** (not the abbreviated form).
Abbreviated SHAs can collide over time; the full SHA is permanent.

The `<one-line bug description>` is a human-readable summary of the bug,
derived from the fix commit's subject or body. It should answer: "what was
broken before this fix?"

## Per-Framework Placement

See [Framework Detection](framework-detection.md) for the per-framework code
examples. The placement summary:

| Framework | Placement | Syntax |
|-----------|----------|--------|
| Vitest / Jest | Comment above `it()` | `// Regression test for fix <sha> — ...` |
| pytest | Function docstring | `"""Regression test for fix <sha> — ..."""` |
| Go testing | Comment above `func` | `// Regression test for fix <sha>: ...` |
| Rust | Doc comment above `#[test]` | `/// Regression test for fix <sha> — ...` |
| JUnit | Javadoc above `@Test` | `/** Regression test for fix <sha> — ... */` |
| RSpec | Comment above `it` | `# Regression test for fix <sha> — ...` |

## Why Not the File Header

Putting the SHA in a file-level comment is a common mistake. A single test
file may contain regression tests for multiple fixes. A file-level comment
either:

- Lists all SHAs (becomes stale as tests are added — easy to forget)
- Lists one SHA (implies all tests in the file are for that fix — wrong)

The reference belongs on the **individual test** so the lineage is precise
and survives refactors that move tests between files.

## When the Fix Is a Squash Merge

If the fix commit is a squash merge (common in GitHub PR workflows), the
single commit SHA is the correct reference — it is the permanent record of
the fix. Do not try to reference the original branch commits; they are
not in the main history.

## When the Fix Is a Revert of a Revert

Track the SHA of the commit that restored the correct behavior (the outer
revert). The bug description should note it is a revert-of-revert:

```
Regression test for fix <sha> — revert of revert restored correct discount
logic that was broken by <bad-sha>
```

## Verification

After authoring, verify the SHA reference is valid:

```bash
git show <sha> --stat   # should show the fix diff
```

If the SHA does not exist (e.g., it was from a force-pushed branch that was
rewritten), the test should reference the closest permanent commit or note
the SHA was lost to history. This is rare; most fixes are on `main`.
